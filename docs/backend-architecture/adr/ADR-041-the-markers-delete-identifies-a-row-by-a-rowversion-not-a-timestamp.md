# ADR-041 — The marker's delete identifies a row by a rowversion, not a timestamp

**Decision.** `IdempotencyMarkers` gains a `rowversion` column, and
[§9.5](../09-messaging.md)'s marker purge selects it and joins on it where it
joined `CommittedAt`. The delete's identity becomes `(Key, RowVersion)`. The
column is an EF **shadow property** declared by each service's own
`IEntityTypeConfiguration` beside the schema, named from
`IdempotencyMarker.RowVersionColumn` so the mapping and the two statements that
read it cannot drift apart. `CommittedAt` keeps its default, keeps its index
and keeps ageing the candidate `SELECT`; what it stops doing is saying which
row is which.

**Why.** [ADR-039](ADR-039-the-markers-purge-asks-the-claim-rather-than-out-counting-it.md)
split one statement into select, ask and delete, and bought back the atomicity
that cost by naming the rows the select had returned instead of describing
them. `(Key, CommittedAt)` was that name: a key identifies a *command*, so past
[§8.5](../08-caching-redis.md)'s guarantee a retry can commit a fresh marker under
a key an earlier pass already chose, and only the timestamp separated the
replacement from the row that was selected.

**It separated them by construction and nothing enforced it.** A
`datetimeoffset(7)` carries no uniqueness constraint, so two writes under one
key differ in it because a clock ordinarily moves — not because the schema says
they must. A database clock set to the exact 100-nanosecond tick of a row
already at least `RetentionPolicy.IdempotencyWindow` old matches the
replacement, and the stale delete removes a row inside its window with a live
claim behind it. The retry after that runs a committed command a third time,
silently.

**That is a fifth clock fault and not a smaller instance of the four before
it**, which is why ADR-039 filed it rather than adding a predicate. The three
predicates that failed on the way to identity each fell to a drift of
sufficient *magnitude* in a direction — a forward step, a backward step, a step
and its correction — and each was closed at the source. This one needs an exact
*coincidence*. A margin cannot be set against it, because there is no quantity
to bound.

**A `rowversion` answers all five at once by reading no clock at all.** It is
SQL Server's own database-wide counter: unique, monotonic, generated by the
engine, and — for a row nothing ever updates — carried unchanged for the life
of that row. It is the identity the join wanted, where the timestamp was
standing in for one.

**Consequences.**

- **Every service gains a migration, and §4.5's scaffold ships it.**
  `AddIdempotencyMarkerRowVersion` adds one column to one table in each of
  Catalog and Ordering, and the scaffold's template migrations go from six to
  seven. The DDL is `ALTER TABLE … ADD [RowVersion] rowversion NOT NULL` with
  no backfill: SQL Server stamps every existing row as part of the `ALTER` and
  every insert after it, which is why a `NOT NULL` column arrives on a
  populated table without a data migration.
- **A service that maps the table and omits the column fails its own purge**,
  loudly and on the first pass — `Invalid column name 'RowVersion'` — rather
  than deleting the wrong row quietly. That is the direction this family of
  faults should fail in, and it is why the scaffold carries the migration
  rather than leaving it to a service author.
- **No CLR property backs it, and that is a decision rather than an
  omission.** Nothing in C# reads the column through EF: the only reader is the
  purge's own SQL, over Dapper, which does not consult the model. A property
  would be a mutable array on a public type that exists to be ignored. The
  const that names the column is what keeps the mapping and the statements
  agreeing, and a per-service test reads the model to prove the property is
  there, is shadow, is store-generated and is not nullable, and reads
  `sys.columns` back for the type — which is the assertion that refuses a plain
  `binary(8)`, since a column of that type would satisfy every other one.
- **The delete still costs two parameters a row**, so the 900-row chunk and the
  2,100-parameter ceiling behind it are unchanged. A `rowversion` is eight
  bytes and the parameter is sized to eight, because an unsized binary
  parameter travels as `varbinary(max)` and would make the `VALUES` list a
  derived table of max-length columns.
- **`CommittedAt` is not dropped, and ADR-038's argument for its default is
  untouched.** The column default and the SQL cutoff that reads it are still
  one clock's arithmetic, and that is still what ages a candidate. Both halves
  of ADR-038 remain load-bearing; only the delete changed.
- **The test that proves it can be written from this side, where ADR-039's
  could not.** No suite owns the container's clock, so the coincidence cannot
  be staged as a clock movement — but it can be staged as its effect: a
  replacement written under the same key *and the same `CommittedAt`*, landed
  between the pass's select and its delete by decorating the claim store the
  pass asks in between. The case was observed red against the previous
  identity, deleting the replacement where it must delete nothing.
- **The residual this leaves is none.** ADR-039 ended with one open item
  besides this — the claim expiring under a running handler
  ([#127](https://github.com/alexander-shamray/blueprint-backend/issues/127))
  — and it is §8.5's, unchanged, and still the only one.
